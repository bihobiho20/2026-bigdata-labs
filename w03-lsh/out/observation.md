# Week 3 관찰

## Task 1 — Minhash와 LSH
행을 한 번씩 순회하며 각 행의 해시 값을 한 번만 계산하고, 그 행을 포함하는 모든 열의 최솟값을 갱신했다. 열마다 행을 다시 순회하는 방식보다 행 단위 데이터 스트림에 적용하기 적합하다.
서명 길이가 bands로 나누어떨어지지 않으면 ValueError를 발생시키기로 했다. 남는 서명 값을 버리지 않고, 모든 band가 같은 크기가 되도록 입력을 수정하게 한다.
교재 예제에서 S1–S4의 서명 일치율은 1.0이지만 실제 Jaccard 유사도는 2/3이다. 독립적인 해시 함수 수를 늘리면 추정 오차를 줄일 수 있지만, 서명 계산 시간과 저장 공간이 증가한다.

## Task 2 — 크기별 시간과 메모리
Ryzen 5 7500X3D, RAM 32GB, Windows 11에서 측정했다. 속도 교차 구간은 875~1,000개였고, 측정값 중 LSH가 처음 빨라진 크기는 1,000개였다. 작은 크기에서는 서명 생성과 banding 준비 비용 때문에 완전탐색이 더 빨랐다.
문서 수를 두 배로 늘릴 때 완전탐색 시간은 3.91~4.14배가 되어 이차 증가와 대체로 일치했다. 실제 문서 수와 n(n-1)/2 비교 횟수도 확인했다.
8,000개에서 완전탐색 137.87초로 시간 부담에 먼저 도달했다. LSH는 12.24초였고, 추가 Python 할당 peak는 완전탐색 18.70 KiB, LSH 28.734 MiB였다(입력 데이터 제외).

## Task 3 — LSH 후보 비교
해시 120개, band 30개, band당 4행을 사용했다. 이론상 후보 확률은 1-(1-s^4)^30이며, s=0.6에서 약 98.45%, 전이점은 (1/30)^(1/4)≈0.427이다. 임계값 0.6보다 낮게 잡아 후보 증가를 감수하고 누락을 줄였고, 실제 재현율은 100%, 비교는 2,246,140회에서 127회로 줄었다.
해시 수를 유지하고 band를 10개(12행씩)로 줄이자 전이점이 약 0.825로 높아졌다. s=0.6의 이론상 후보 확률은 약 2.16%였고, 실제 전체 재현율은 30.58%(121쌍 중 37쌍)로 떨어졌다.
해싱 비용은 비교 횟수 점수에 포함되지 않지만 실제 실행 시간에는 포함된다. 문서 수·shingle 수·해시 수가 커지거나 후보 비교가 이미 매우 적으면, 서명 생성 시간과 메모리가 큰 비용이 되므로 비교 횟수만으로 성능을 판단하기 어렵다.
